# Ce que CAPI Helm applique aux groupes Kubernetes

Un membre du projet peut vouloir un pool généraliste et un pool de calcul dans le même cluster. Avec les deux révisions CAPI Helm examinées, chaque groupe de workers alimente une entrée `nodeGroups` du chart avec un nom, un flavor et un nombre de machines. Le projet peut donc demander des capacités de VM différentes par pool. L’image Kubernetes, en revanche, vient du modèle de cluster dans la construction des valeurs Helm. Magnum choisit le pilote à partir du modèle, par nom explicite ou selon le triplet type de serveur, OS, orchestrateur. | Demande de l’utilisateur | Effet lu dans le pilote |
|---|---|
| Ajouter, modifier ou supprimer un pool | Les méthodes du pilote modifient le statut du groupe et recalculent la release Helm. Les workers sont suivis par leur `MachineDeployment`. Pour une suppression, l’entrée sort des valeurs attendues, puis le pilote suit la disparition du groupe. |
| Choisir un flavor | Le pilote vérifie l’identifiant ou le nom ainsi que les minima configurés de RAM et de vCPU. Il transmet le flavor du groupe au chart. Garder la convention des noms déjà utilisée par le fork. |
| Modifier le nombre de workers ou les bornes | `machineCount` provient du groupe. Lorsque l’autoscaling est activé au niveau cluster et que les bornes diffèrent, le pilote fournit `machineCountMin` et `machineCountMax`. Le worker par défaut a un traitement particulier des labels de cluster `min_node_count` et `max_node_count`. |
| Demander un minimum de zéro avec autoscaling | Le fork du pilote refuse un minimum inférieur à un dans cette validation. La révision officielle examinée admet zéro si le chart prend en charge le scale-to-zero (version ≥ 0.26.0). Ne déduire aucune de ces capacités de la seule microversion 1.10. |
| Utiliser une image propre au pool, une zone par label Magnum, des labels Kubernetes ou des taints | Ces champs peuvent exister dans l’objet Magnum. La projection des valeurs Helm par groupe dans les deux révisions ne transmet ni `ng.image_id`, ni une AZ lue sur `ng.labels`, ni `ng.node_labels` ou `ng.node_taints`. Relire l’objet Magnum ne démontre donc pas leur application aux machines ou aux nœuds. |
| Retirer une VM précise | `resize_cluster` journalise que `nodes_to_remove` n’est pas pris en charge et réconcilie la release. La réduction du nombre demandé peut réussir en supprimant une autre machine. |
| Redimensionner le plan de contrôle | Le pilote redéfinit `validate_master_resize` et réutilise la validation de la taille initiale (entier positif impair). L’opération cible le groupe master existant. |
| Mettre à niveau un seul groupe ou régler le nombre de nœuds traités en parallèle | Le pilote remplace le modèle du cluster, marque tous les groupes en mise à jour et réconcilie la release. Il n’utilise pas `max_batch_size` pour régler le déploiement. Une interface promettant une mise à niveau limitée au pool choisi donnerait une fausse portée à l’action. |

**Vérification à prévoir avant d’annoncer une capacité sur un cloud.** Identifier la révision réellement chargée et le chart du modèle. Pour deux pools de flavors distincts, distinguer le groupe visible dans Magnum, le statut terminal de l’opération et les VM créées avec le flavor attendu. Pour un label ou un taint, la preuve de bout en bout serait sa présence sur les objets Kubernetes `Node` du pool. L’étude présente décrit le code, sans opération sur un cluster.
