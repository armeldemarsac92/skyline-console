# Négocier la microversion Magnum dans Skyline

**Quel appel doit faire le navigateur pour obtenir le même contrat que la CLI ?** Dans le code stable 2026.2 étudié, Magnum annonce **1.1 à 1.14**. Sans en-tête le serveur choisit 1.1. Le plugin `openstack coe` demande par défaut `latest` et transmet une microversion explicite si elle est fournie. Une même URL peut donc fonctionner en CLI et retourner HTTP 406 dans Skyline. | Microversion annoncée | Fonction à laquelle elle correspond |
|---|---|
| 1.2 / 1.3 | Opérations de cluster asynchrones / demande de rollback sur mise à jour |
| 1.4 / 1.5 / 1.6 | Statistiques / rotation de CA / quotas de clusters |
| 1.7 / 1.8 | Redimensionnement / mise à niveau |
| 1.9 / 1.10 | Nodegroups / prise en charge d’un nombre de workers égal à zéro, selon les bornes et le pilote |
| 1.11 / 1.12 | Retrait de `bay` et `baymodel` / rotation du credential du cluster |
| 1.13 | Dans la réponse cluster, `cluster_id` remplace `stack_id` pour l’identifiant d’infrastructure. L’UUID Magnum du cluster reste `uuid`. |
| 1.14 | `node_labels` et `node_taints` sur les groupes de workers |

Ces seuils décrivent le contrat publié. Certains contrôleurs ne vérifient pas individuellement chaque champ ou route à sa version d’introduction. Pour la compatibilité entre installations, se baser sur le seuil annoncé. [Historique de la série](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/rest_api_version_history.rst) · [Contrôleur des clusters](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/cluster.py)

Dans le fork, `magnumBase()` passe par le catalogue d’endpoints. `apiVersionMaps` ne définit aucune valeur générale pour Magnum. `ClustersStore.resize` transmet explicitement `OpenStack-API-Version: container-infra latest` tandis que `upgrade` ne fournit aucun en-tête. Le détail cherche encore la stack Heat avec `item.stack_id`. Forcer toutes les lectures à `latest` changerait cette réponse sur un serveur ≥ 1.13. Un pilote CAPI peut en outre utiliser ce champ pour identifier une release Helm. [Endpoints et versions Skyline](https://github.com/armeldemarsac92/skyline-console/blob/5a8ca40e86cbcbacf725b38fc14ca5acbed1e19a/src/client/client/constants.js) · [Store cluster Skyline](https://github.com/armeldemarsac92/skyline-console/blob/5a8ca40e86cbcbacf725b38fc14ca5acbed1e19a/src/stores/magnum/clusters.js) · [Attribution de l’identifiant par le pilote](https://github.com/armeldemarsac92/magnum-capi-helm/blob/374459d2026a0fe359d252aa0ba8ea85e3acd498/magnum_capi_helm/driver.py#L1250)

**Conséquence pour les nodegroups.** Découvrir `min_version` et `max_version` à la racine du service Magnum de la région. Si le catalogue fournit déjà une URL en `/v1`, préserver son préfixe de déploiement. Les réponses de `/v1/` fournissent aussi les en-têtes de versions minimale et maximale. Pour lister les groupes, sélectionner un contrat explicite tel que `OpenStack-API-Version: container-infra 1.9`. Pour envoyer des labels Kubernetes, demander 1.14 si le service l’annonce, puis vérifier la prise en charge du pilote.
