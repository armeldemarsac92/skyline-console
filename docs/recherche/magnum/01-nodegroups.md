# Groupes de nœuds Kubernetes

Un utilisateur peut ajouter des workers d'un flavor Nova différent à un cluster existant, puis suivre l'état de ce groupe avec `openstack coe nodegroup`. CAPI Helm 1.4.0 transmet le flavor du groupe au chart. Les champs de placement Kubernetes ne sont pas transmis par cette version. [Guide Magnum, « Node Groups »](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/doc/source/user/node-groups.rst), [pilote CAPI Helm](07-pilote-capi-helm.md).

Dans `kube-prod`, cet exemple crée un groupe `workers-compute` de deux nœuds avec le flavor illustratif `compute.large` et des bornes de 1 à 3. Ces bornes respectent le minimum de 1 exigé par CAPI Helm 1.4.0 lorsque l’autoscaling est activé. Une fois le groupe visible, `show` permet de lire `status` et `status_reason`. [Options et corps de `CreateNodeGroup`](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py#L25), [`ShowNodeGroup`](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py#L232).

```bash
openstack coe nodegroup create kube-prod workers-compute --flavor compute.large --node-count 2 --min-nodes 1 --max-nodes 3
openstack coe nodegroup show kube-prod workers-compute
```

```http
POST /v1/clusters/kube-prod/nodegroups/
OpenStack-API-Version: container-infra latest
Content-Type: application/json

{"name":"workers-compute","node_count":2,"max_node_count":3,"min_node_count":1,"role":"worker","flavor_id":"compute.large"}
```

Le `POST` retourne `202` avec l'UUID du groupe. Le `show` appelle `GET /v1/clusters/kube-prod/nodegroups/workers-compute`. [Routes du client](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/v1/nodegroups.py#L55), [contrôleur Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L429).

Au commit Skyline `5a8ca40e86cbcbacf725b38fc14ca5acbed1e19a`, la fiche cluster affiche les compteurs globaux `master_count` et `node_count` dans son unique onglet **Détail**. Le client Magnum expose les clusters, leurs modèles et les quotas. Les cinq opérations sur les groupes manquent dans les vues projet et administration. [Client Skyline](../../../src/client/magnum/index.js), [onglet de détail](../../../src/pages/container-infra/containers/Clusters/Detail/index.jsx), [compteurs de la fiche](../../../src/pages/container-infra/containers/Clusters/Detail/BaseDetail.jsx), [actions projet et administration](../../../src/pages/container-infra/containers/Clusters/actions/index.jsx).

Les contrats ci-dessous proviennent de Magnum et de `python-magnumclient` sur `stable/2026.2`, aux révisions indiquées dans les liens. La référence API publiée ne consacre aucune section au CRUD des groupes. Le montage du contrôleur dans `ClusterController` et le client Python donnent les chemins effectivement utilisés. [Référence API Magnum](https://docs.openstack.org/api-ref/container-infrastructure-management/), [index de la référence à la révision étudiée](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/api-ref/source/index.rst), [montage dans `ClusterController`](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/cluster.py#L396), [`NodeGroupManager._path`](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/v1/nodegroups.py#L55).

## Commandes et routes

`<cluster>` et `<groupe>` acceptent un nom ou un UUID. Les groupes sont résolus dans le cluster indiqué. Le CLI emploie un slash final pour la collection. Dans les règles de policy, la route descriptive de `nodegroup:get` contient le singulier `nodegroup`. Le contrôleur et le CLI emploient `nodegroups` pour toutes les opérations. [Commandes OSC](https://docs.openstack.org/python-openstackclient/latest/cli/plugin-commands/magnum.html#coe-nodegroup-create), [implémentation OSC](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py), [contrôleur Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L357), [règles `nodegroup:*`](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/common/policies/nodegroup.py).

| Après `openstack coe nodegroup` | Route Magnum | Résultat HTTP |
| --- | --- | --- |
| `list <cluster>` | `GET /v1/clusters/{cluster}/nodegroups/` | `200`, tableau sous la clé `nodegroups` et lien `next` lorsqu'une page est pleine |
| `show <cluster> <groupe>` | `GET /v1/clusters/{cluster}/nodegroups/{groupe}` | `200`, objet du groupe |
| `create <cluster> <nom>` | `POST /v1/clusters/{cluster}/nodegroups/` | `202`, objet avec l'UUID attribué avant le traitement |
| `update <cluster> <groupe>` | `PATCH /v1/clusters/{cluster}/nodegroups/{groupe}` | `202`, objet qui porte les valeurs demandées |
| `delete <cluster> <groupe> […]` | `DELETE /v1/clusters/{cluster}/nodegroups/{groupe}` | `204`, traitement asynchrone. Le CLI adresse une requête par groupe |

`list` expose `--limit`, `--sort-key`, `--sort-dir` et `--role`. REST accepte aussi `marker`. Le filtre `role` correspond à une valeur exacte. `next` transporte le marqueur et le tri, alors que le contrôleur ne lui transmet pas le filtre `role`. Pour conserver un filtre côté interface, réutiliser le rôle demandé dans chaque requête paginée. La collection REST contient notamment `is_default`, exploitable par Skyline pour reconnaître les groupes protégés. La sortie tabulaire de `openstack coe nodegroup list` affiche seulement l’UUID, le nom, le flavor, l’image, l’effectif, le statut et le rôle. [Colonnes de la CLI](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py#L217). `show` donne les valeurs détaillées, dont les bornes, les adresses des nœuds, les labels, les taints et `status_reason`. [Collection et filtres Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L334), [calcul de `next`](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/collection.py#L30), [`NodeGroup.convert`](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L292), [`NODEGROUP_ATTRIBUTES` du client](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/v1/nodegroups.py#L19).

## Rôles et groupes par défaut

Magnum crée `default-master` (`role=master`) et `default-worker` (`role=worker`) avec `is_default=true`. Un groupe supplémentaire prend le rôle `worker` par défaut. Le CLI accepte aussi un rôle d'usage libre, par exemple `batch`, partageable par plusieurs groupes. `master` est réservé et sa création par le CRUD renvoie `400`. Le guide présente `magnum.openstack.org/role` et `magnum.openstack.org/nodegroup` comme labels Kubernetes pour le placement. CAPI Helm 1.4.0 ne produit pas ces labels dans la projection du groupe au chart. [Création des groupes par défaut](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/conductor/utils.py#L156), [guide des rôles](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/doc/source/user/node-groups.rst#L31), [contrôleur de création](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L447).

La protection contre la suppression repose sur `is_default` et couvre les deux groupes, avec `400`. Le guide décrit `default-worker` comme impossible à reconfigurer. Le contrôleur PATCH autorise les bornes et, sur un worker, les labels et taints de nœuds, sans verrou `is_default`. La modification de l'effectif passe par le resize du cluster. Pour un changement de flavor, le parcours décrit dans le guide consiste à créer un groupe supplémentaire avec le flavor voulu et à migrer les charges de travail avant de retirer un ancien groupe supprimable. [Guide](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/doc/source/user/node-groups.rst), [`NodeGroupPatchType` et contrôleur](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L322), [tests PATCH et DELETE](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/tests/unit/api/controllers/v1/test_nodegroup.py#L597).

## Création et modification

| Propriété | Option de création | Effet et valeur par défaut |
| --- | --- | --- |
| `name`, `role` | `<nom>`, `--role` | Nom unique dans le cluster, rôle `worker` par défaut |
| `node_count`, `min_node_count`, `max_node_count` | `--node-count`, `--min-nodes`, `--max-nodes` | Entiers positifs ou nuls, défauts `1`, `0`, `null` |
| `flavor_id`, `image_id` | `--flavor`, `--image` | Le flavor des workers du cluster et l'image du modèle du cluster sont repris par défaut |
| `docker_volume_size` | `--docker-volume-size` | Taille du volume Docker en Go, au moins `1` si renseignée |
| `labels`, `merge_labels` | `--labels`, `--merge-labels` | Sans `labels`, copie des paramètres Magnum du cluster. Avec `labels`, remplacement par défaut ou fusion si `merge_labels=true`, avec priorité aux valeurs du groupe |
| `node_labels`, `node_taints` | `--node-labels`, `--node-taints` | Labels de nœuds sous forme de dictionnaire texte vers texte. Taints sous forme de liste d'objets avec `key`, `effect` et `value` facultative |

Le POST attend que le cluster dispose d'une `api_address`. Une adresse absente, un nom déjà utilisé ou des bornes incompatibles donnent `409`. La règle vérifie `min_node_count ≤ node_count` et, si `max_node_count` est renseigné et non nul, `node_count ≤ max_node_count`. Dans ce code un maximum à zéro ne déclenche donc pas la vérification du plafond. Le contrôleur vérifie aussi le disque racine du flavor quand `boot_volume_size`, lu dans les paramètres du cluster ou la configuration Magnum, vaut zéro. [Options et corps du CLI](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py#L25), [schéma et validation](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L157), [validation du disque racine](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/attr_validator.py#L181), [tests de création](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/tests/unit/api/controllers/v1/test_nodegroup.py#L513).

Les `labels` sont des paramètres d'infrastructure Magnum. La fiche détaillée expose `labels_overridden`, `labels_added` et `labels_skipped` pour comparer le groupe au cluster. Les `node_labels` et `node_taints` concernent les nœuds Kubernetes. Magnum refuse les labels de certains espaces de noms réservés du kubelet, ainsi que les labels et taints non vides sur le rôle `master`. Pour les taints, la clé doit être renseignée et `effect` prend les valeurs `NoSchedule`, `PreferNoSchedule` ou `NoExecute`. Magnum accepte et enregistre ces champs. CAPI Helm 1.4.0 ne les transmet pas au chart et leur présence dans la fiche du groupe ne garantit aucun placement de workloads. [Validations Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L40), [différence des paramètres](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/nodegroup.py#L292), [valeurs Helm par groupe](https://opendev.org/openstack/magnum-capi-helm/src/commit/a8b82c2480a286a10b60ecc1d94c6cd9f1d01823/magnum_capi_helm/driver.py#L986).

`update` envoie un tableau JSON Patch avec `replace` sur `/min_node_count`, `/max_node_count`, `/node_labels` ou `/node_taints`. Le CLI remplace la collection entière de labels ou taints quand l'option est fournie et la vide si l'option reçoit `''`. Le POST transmet ces collections en JSON natif. Pour le PATCH, le CLI transmet une représentation en chaîne et Magnum la convertit avec `ast.literal_eval` après la validation du type `texte ou entier`. L'API permet aussi `remove` sur les bornes, ce qui rétablit `0` pour le minimum et `null` pour le maximum. Le CLI `update` expose uniquement les remplacements. [Assemblage du patch dans `UpdateNodeGroup`](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/v1/nodegroups.py#L269), [type `JsonPatchType`](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/types.py#L151), [décodage REST](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/utils.py#L71), [tests de remplacement et suppression](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/tests/unit/api/controllers/v1/test_nodegroup.py#L732).

L'exemple dédie aux tâches batch un groupe worker `batch` déjà présent dans `kube-prod`. Les workloads qui doivent s'y placer utilisent le label `workload=batch` et une tolérance au taint correspondant. [Option de microversion OSC](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/osc/plugin.py#L19), [conversion des taints](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/common/utils.py#L138), [en-tête du client HTTP](https://opendev.org/openstack/python-magnumclient/src/commit/cf374db1a93cc0fe8d326a61333837e3b7eeb0e9/magnumclient/common/httpclient.py#L348).

```bash
openstack --os-container-infra-api-version 1.14 coe nodegroup update kube-prod batch \
  --node-labels workload=batch --node-taints workload=batch:NoSchedule
```

```http
PATCH /v1/clusters/kube-prod/nodegroups/batch
OpenStack-API-Version: container-infra 1.14
Content-Type: application/json

[
  {"op":"replace","path":"/node_labels","value":"{'workload': 'batch'}"},
  {"op":"replace","path":"/node_taints","value":"[{'key': 'workload', 'value': 'batch', 'effect': 'NoSchedule'}]"}
]
```

## Conditions d'intégration dans Skyline

- **Microversions.** `1.9` introduit le CRUD, `1.10` officialise les groupes à zéro nœud dans la création et le redimensionnement du cluster, et `1.14` introduit les labels et taints Kubernetes. Au SHA étudié, le contrôleur de nodegroups déclare toutes ses méthodes à partir de `1.9` et partage le même schéma, y compris pour les champs introduits en `1.14` et l'effectif à zéro dans le POST de groupe. Pour une interface portable, la découverte à la racine fournit `min_version` et `max_version`. Demander explicitement une version compatible et exposer labels et taints à partir de `1.14`. Le serveur part de `1.1` sans en-tête, le CLI étudié demande `latest` par défaut et Skyline ne déclare pas de règle de microversion Magnum. [Historique des versions](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/rest_api_version_history.rst#L85), [routage et en-têtes Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/api/controllers/v1/__init__.py#L225), [découverte](https://docs.openstack.org/api-ref/container-infrastructure-management/#api-versions), [paramètres de version Skyline](../../../src/client/client/constants.js).
- **Autorisations.** `nodegroup:get_all` et `nodegroup:get` visent par défaut un lecteur du projet ou un administrateur. La lecture interprojets déclenche les règles admin `nodegroup:get_all_all_projects` et `nodegroup:get_one_all_projects`. `nodegroup:create`, `nodegroup:update` et `nodegroup:delete` visent un membre du projet ou un administrateur. Les policies du cloud et l'accès effectif à la ressource déterminent les actions disponibles. [Policies Magnum des groupes](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/common/policies/nodegroup.py), [rôles de base Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/common/policies/base.py#L18).
- **Suivi asynchrone.** Après acceptation, le conductor passe le cluster en `UPDATE_IN_PROGRESS` et le groupe en `CREATE_IN_PROGRESS`, `UPDATE_IN_PROGRESS` ou `DELETE_IN_PROGRESS`. Pour la création et la mise à jour, `allowed_operation` vérifie le statut du groupe lorsqu'il est présent. En cas d'exception du driver, le groupe reçoit le statut `*_FAILED` correspondant et `status_reason`. Un onglet **Groupes de nœuds** peut afficher le statut par groupe, récupérer le motif dans le détail et suivre les mises à jour ou la disparition du groupe après suppression. Les capacités et le résultat du driver restent à vérifier sur le cloud cible. [Handler du conductor](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/conductor/handlers/nodegroup_conductor.py#L33), [interface des drivers Magnum](https://opendev.org/openstack/magnum/src/commit/68befbf84e8ec50e57dee682cea9398bba606904/magnum/drivers/common/driver.py#L278).
